# Public decompilation progress and full-executable inventory

[Snail Mail on decomp.dev](https://decomp.dev/banteg/snail) reports the complete
Windows gameplay executable as `win32-reflexive`. This integration follows
[Crimson’s evidence-backed custom reporting](https://github.com/banteg/crimson/blob/master/analysis/decomp/README.md).
The comparison is performed by `snail match`, not objdiff; objdiff v3.8.1 validates
the v2 report format. Library recovery remains separate work.

## Target and native evidence

The target is the unwrapped gameplay executable, not the Reflexive launcher,
external DLLs, installer, or asset archive. Version ID:
`win32-reflexive`. No PE version resource was found in the gameplay executable,
wrapped image, or launcher; this ID does not assert a numeric retail version.

SHA-256: `d365acf3db5335dded4dfd944e876ee2f23156595503693e0bf1baee1c8c83e5`.

The three snapshots were captured on 2026-09-07 from Binary Ninja
5.4.10406-dev Personal, IDA 9.4, and Ghidra 12.1.2. Ghidra used the existing
Windows analysis project, read-only, with analysis disabled; its version matches
that project's metadata. This was not a fresh import. IDA ran on a temporary
database copy. Neither original database was edited. Every executable section's
bytes and virtual bounds were checked against the original PE. IDA and Ghidra
also verified their recorded input SHA-256.

The raw section has another **568 bytes of file alignment**, outside the virtual

This is a conservative native-code inventory, not a claim that all 596,823 bytes
are proven instructions. The custom report uses this fixed code accounting,
rather than claiming to reconstruct original COFF symbol sizes. In particular:

- 588,382 bytes are instructions in all three analyzers.
- IDA finds 397 code bytes absent from Binary Ninja's basic blocks. Ghidra
  corroborates 159 of these. They include exception/runtime paths.
- Binary Ninja counts 31 bytes that IDA calls alignment. They remain included.
- Ghidra calls four 4-byte ranges data where both other tools find code:
  `0x433678`, `0x433904`, `0x434044`, `0x434064`. They remain included.
- Ghidra adds no instruction bytes outside the BN/IDA union.
- Of the excluded data, 2,942 bytes are classified as data by both IDA and
  Ghidra; 6,864 are IDA data and Ghidra unknown. Thus this is not unanimous
  classification of every excluded byte.

Function-start counts differ: BN 2,259; IDA 2,051; Ghidra 1,814. Their union has
2,286 **candidates**, not 2,286 established independent functions. Thunks,
shared tails, exception chunks, and padding-only analyzer functions need an
ownership policy before publishing a function-count denominator. The generator
unions byte ranges so overlapping/shared tails never inflate byte totals.

The 785 curated starts own 310,123 of the retained bytes under the union of
analyzer function bodies. Another 286,700 lie outside those curated bodies;
this does not identify them all as libraries. The legacy status denominator
uses intervals between curated starts and cannot substitute for this inventory.
There are 47 retained code bytes outside all exported function bodies.

## What decomp.dev actually specifies

The project's [officially linked guide](https://decomp.wiki/tools/decomp-dev)
explicitly permits reports generated by custom tooling using the schema. Its
objdiff integration guide asks for every linked object, permits a null source
object for unrecovered units, and warns against crediting copied assembly as
decompilation. Report artifacts are uploaded on the default branch before an
administrator registers the project. The standard workflow builds sources and
generates the report in CI. Merely uploading committed local measurements is
technically ingestible but is not that documented reproducible build workflow.

The following definitions come from the actual
[objdiff report generator](https://github.com/encounter/objdiff/blob/fba10a617154f19b3fc25c8817dc81f81d8489b5/objdiff-cli/src/cmd/report.rs),
not an inferred site-wide rule about PE layout:

| Field | Generator semantics |
| --- | --- |
| `total_code` | Sum of eligible target symbol sizes in code sections; not PE file size or raw instruction coverage. Hidden/ignored/section symbols and zero-sized symbols are skipped. |
| `matched_code` | Entire target symbol size when its comparison score is exactly 100%; no fractional exact-match credit. |
| `fuzzy_match_percent` | Sum of target symbol size times symbol score, divided by `total_code`. Missing source normally scores zero. |
| `complete_code`, `complete_data` | Whole-unit totals when that unit's `metadata.complete` is true. This is independently supplied metadata. |
| `total_data`, `matched_data` | Data/BSS section sizes; a section contributes matched bytes when its section score is 100%. |

The CLI has a complete-with-no-target fallback that assumes a match; we should
not use that shortcut as proof. `complete` is documented as linked in the
[configuration README](https://github.com/encounter/objdiff/blob/fba10a617154f19b3fc25c8817dc81f81d8489b5/README.md).
decomp.dev displays matched code as its decompiled headline and linked code
separately in its [report UI](https://github.com/encounter/decomp.dev/blob/e9c086adb74d2fe569541cd715cd9312d7641313/crates/web/src/handlers/report.rs).

Objdiff's [instruction comparison](https://github.com/encounter/objdiff/blob/fba10a617154f19b3fc25c8817dc81f81d8489b5/objdiff-core/src/diff/code.rs)
uses weighted penalties for insertions, replacements, register differences, and
immediates. It is not our SequenceMatcher ratio. The report generator defaults
to relaxed function relocations, so its 100% also does not establish raw
whole-executable byte identity or validate the meanings of every referenced
symbol. Our reference audit remains useful additional proof.

## Adopted public policy

- **Denominator:** every retained code byte in the original gameplay executable,
  including game/platform code, static libraries, runtime helpers, and unknown
  code. No port-relevance filter. Code-section data and uncontested alignment are
  outside the code measure; data progress is not reported.
- **Units:** disjoint native function-body code ranges, not recovered original
  translation units. Curated owners take priority, then BN, IDA, and Ghidra;
  within each class the highest entry address owns shared ranges. Empty duplicate
  owners are omitted. Every byte is counted once. Five unassigned code runs are
  explicit zero-progress units, without invented function-count credit.
- **Matched:** an actual source-built scratch with 100% normalized instruction
  identity and a clean reference audit. Its tested native extent must cover all
  code assigned to the public function. Library identification, prebuilt objects,
  copied assembly, and generated thunks receive no decompiled credit.
- **Fuzzy:** `snail match` similarity, weighted by owned original code bytes across
  the full denominator. Code outside the tested scratch extent earns zero.
  A 100% instruction score lacking exact/reference/extent proof is capped at
  99.99% in the display, preventing misleading green exact-match tiles. These
  custom scores are not numerically equivalent to objdiff's weighted penalties.
- **Linked:** zero. Scratch compilation and semantic-complete metadata do not
  establish an integrated source reconstruction or original translation units.
- **Data:** omitted, not claimed complete. Recovered types and original data bytes
  alone do not establish matching source-built data/BSS layout.

The initial public inventory has 2,261 nonempty function owners plus five
unassigned-range units. This is a deterministic reporting partition of the
analyzer candidates, not proof of 2,261 original source functions. Boundary fixes
must regenerate the native inventory and matching evidence together. The
`construct_game_runtime` owner includes an out-of-line tail beyond its tested
scratch, and `abort_startup_with_3d_error` retains five disputed padding bytes;
these do not receive whole-function matched credit.

## Refresh and publish

On a machine with the pinned original gameplay executable and compiler bundles:

```sh
uv run snail match report --refresh -j 8
```

Refresh verifies the original SHA-256, recomputes the native inventory, freshly
compiles every scratch, rejects failures, and stores
`analysis/progress/win32-reflexive.json`. The evidence includes source/config/
manifest/reporter hashes, every compiler-bundle file hash, Wibo identity, original
image identity, owned ranges, reference audit results and measured scores. Build
inputs must remain unchanged throughout the evaluation. Refresh invalidates the
legacy scratch build/status cache because that cache does not fingerprint every
compiler backend DLL.

To validate saved evidence and write `artifacts/decomp/report.json`:

```sh
uv run snail match report
```

CI performs this portable validation on pushes to `master` and PRs. It rejects
added, changed, or deleted scoring/build inputs, verifies the full public
partition and source/reference/extent credit, runs the SHA-256-pinned objdiff
parser, and uploads only `report.json` as `win32-reflexive_report`. No game bytes
or compiler binaries are uploaded. Unlike Crimson's current workflow, CI does
not download the reference images: the hashed, byte-verified analyzer snapshots
are the portable inventory evidence. Present local images/compiler bundles are
checked against the stored identities. This is saved-result verification, not a
claim that CI recompiled proprietary inputs.

Commit refreshed evidence alongside scoring, source, shared-header, config, or
native-inventory changes. `README.md`, research notes and experiment logs do not
affect scores. Registration uses game name **Snail Mail**, platform **Windows**.

Library recovery is deferred. Existing strings include zlib 1.2.1 banners,
libpng 1.2.5, older zlib 1.1.3/PNG 1.0.5 leads, and a JPEG copyright signature.
Multiple copies and mixed compiler provenance remain possible. These are
future attribution leads, not recovered-library ranges or match credit.

## Files and reproduction

- `binja-code-inventory.json`: merged native basic-block ranges per function.
- `ida-code-inventory.json`: complete section classification and function chunks.
- `ghidra-code-inventory.json`: complete section classification and function bodies.
- `executable-code-inventory.json`: generated partition, evidence hashes, and
  candidate ownership; not an objdiff-format report.

Regenerate from the saved snapshots and original executable:

```sh
uv run tools/report_code_inventory.py
uv run tools/report_code_inventory.py --check
uv run pytest -q tests/test_code_inventory.py
```

The three native exporters are `tools/binja/export_code_inventory.py` (run via
`bn --target SnailMail_unwrapped.exe.bndb py --script ... --format json` and save
its `result` object), `tools/ida/export_code_inventory.py` (IDAPython arguments:
original PE, output JSON), and `tools/ghidra/ExportCodeInventory.java` (arguments:
JSON containing `input_sha256` plus expected executable `sections`, output JSON).
The Ghidra section specification uses `name`, `start`, `end`, `sha256` from a
PE-verified snapshot. Use a temporary copy of each headless database/project;
Ghidra accepts `-process SnailMail_unwrapped.exe -noanalysis -readOnly`.
`snail.code_inventory.snapshot_text` normalizes snapshots for stable diffs.
